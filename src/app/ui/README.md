# OpenDoc UI

Use Base UI for interactive controls. The app uses plain CSS and local fonts; PDF document themes remain independent of the browser UI.

Text fields use a fine blue focus edge on the existing border with a soft 3px glow. Keep the edge flush with the control; search fields own focus on their wrapper, without a second ring on the inner input.

- `Button` preserves the Base UI props, refs, and `render` composition API. Use the `primary`, `text-button`, or `icon-button` class for the existing visual treatments. Standard buttons use a 32px minimum height and 6px radius, with 32px sidebar/menu rows and 40px document list rows. On touch screens (`pointer: coarse`) `--control-hit-size` rises to 40px, so buttons, search fields, selects, and links sized from it reach a 40px target without changing fine-pointer sizes; size new controls from that token rather than a fixed height. Sidebar and menu rows retain 44px touch targets. Controls retain a subtle press response; `static` disables press scaling. Use it for document cards, thumbnails, quote anchors, and precise PDF targets. PDF targets also retain their exact geometry instead of adopting minimum control dimensions.
- `Input` is Base UI Input with `dir="auto"`, so typed Arabic and mixed Arabic/English text takes its direction from its first strong character while the app chrome stays left-to-right. Give raw `textarea` fields and blocks that show user or document text (titles, comments, descriptions, guide paragraphs) `dir="auto"`; wrap such text in `<bdi>` when it shares a line with icons or labels. Use logical properties (`padding-inline`, `margin-inline`, `border-inline-start`, `text-align: start`) around that text. Do not mirror the app layout.
- `IconButton` requires an accessible label and provides a tooltip. Pass `hint` with `focusableWhenDisabled` to explain why an action is unavailable; it replaces the tooltip and becomes the accessible description. `HintButton` is a labelled button with the same optional `hint`. `ToggleButton` exposes controlled pressed state. Avoid adding tooltips to already descriptive document cards or PDF hit areas.
- `SelectControl` composes Base UI Select for short, labeled choices. Larger searchable sets should use Base UI Combobox when needed.
- All action menus and dropdown lists use the shared `ui-menu-*` / `ui-select-*` styles in `ui.css`: 12.5px regular labels, 32px rows (44px for touch), 4px popup padding, 6px corners, and compact separators. Action menus start at 184px wide; selects fit their trigger and content within the viewport. Use the `--menu-*` tokens to change density across the system. Domain styles must not override menu type, spacing, or surfaces. Use `ui-menu-item-danger` for destructive actions and `ui-menu-label`, `ui-menu-group`, and `ui-menu-check` for grouped and checked choices. A submenu row names its current choice with `ui-menu-value`. Keep an action menu to about six visible rows in separated groups, with the destructive action last; app-wide settings such as appearance belong in the app menu's submenu, never in a document's actions.
- Compose `Dialog.Trigger`, `Dialog.Close`, and `Dialog.Popup` within the same root so dismissal, focus containment, and focus restoration remain library-owned. Give each dialog a title and description.
- Use Base UI Popover and `ui-popover-popup` for anchored panels containing forms, such as the reader's Export dropdown. Reuse shared fields and `ui-menu-item` action rows; retain touch-aware focus, viewport bounds, and dismissal without losing an in-flight request. Previous exports opens after the dropdown restores focus to its trigger.
- Library pages (Documents, Presentations, projects, Themes, Templates, and Media & Assets) use the one `FilterBar` in `src/app/FilterBar.tsx`, never a page-specific toolbar. Its order is fixed: search; the page's primary dimension as `FilterChoices` buttons with counts (or a page-supplied element such as the theme folder buttons, styled with the same `filter-choice` classes); one **Filter** menu for every secondary dimension, each a submenu of radio rows with counts (a single dimension lists its values directly), with active filters as removable chips beside it; then the sort menu and the gallery/list toggle. Describe dimensions as `Facet`s from `libraryFilters.ts`; `offered` hides any that would not narrow the list, and a chosen value stays visible. Filters and search live in the hash query through `useHashQuery` (search replaces the history entry, other choices push one); sort is a per-page preference through `useSortPreference`. Removing a chip moves focus to the next chip, then **Filter**, then search. The bar is one row while its container allows and moves the primary buttons and filters to a second row below 820px (640px without primary buttons).
- `UiProvider` owns tooltip timing and notifications. Errors stay visible until dismissed; success notices expire and pause while interacting.

`ui.css` owns shared control styling, focus, popup layering, and reduced-motion behavior. `style.css` owns application layout and document surfaces. Keep domain components in `src/app`; add a shared abstraction only when it has a concrete use.

`SkillIndex` is the sidebar's labelled **Skills** entry; `SkillIndexPopup` is the shared non-modal reference popover it opens, also opened from **Agent skills** in the reader's app menu (`AppMenu`). Its entries come from `.agents/skills/opendoc-*/agents/openai.yaml` at build time; edit `display_name` (the readable title) and `short_description` there using JSON-quoted YAML strings and rebuild. The exact skill name stays visible beside each title because agents need it. Keep names aligned with skill folders and frontmatter. The index lists skills for the external agent; it does not execute them.

`DocumentCard` uses Base UI Button around a live PDF.js cover. `PdfPage` remains responsible for canvas rendering, references, and component geometry. Text selection is confined to the floating text editor. Base UI Preview Card is a hover popup, not a PDF renderer. Component hit areas use shared Buttons with hover outlines and keyboard activation. Clicking a target selects it. The selection bar’s Edit and Comment open one shared panel beside the selection.

When changing controls, check keyboard activation, Escape, focus restoration, disabled states, and a narrow viewport. When changing document surfaces, check live covers, fit width, page entry, text selection, inspection, comments, and export. Use a temporary workspace for feedback tests so the user's comment history stays clean.

The app shell uses bundled Geist variable WOFF2 faces, including real italic and the full weight range, from `assets/ui-fonts/geist`, with Arabic-only Noto Naskh Arabic faces from `assets/ui-fonts/noto-naskh-arabic` as the next family for Arabic letters. Document typography belongs to the PDF and theme specimens. UI sizes are explicit at native browser zoom: 20px page headings, 16px card/section titles, 13px body and control text, and 12.5px sidebar labels. Match density through these type and spacing tokens, not global CSS zoom or a transform on the app. Library pages have one title and one primary action, without a second breadcrumb header, promotional subtitle, or repeated document list. The reader uses one toolbar with document context, centered reading controls, and trailing actions. Its document title is the page's h1 at the 16px title size; side panel headings for a drilled-in view (one version, one component's comments) use the 20px page-title size, and a tab whose label already names its list keeps its heading for screen readers only. App-wide items live in one labelled **Skills and appearance** menu (gear) beside the document actions: Agent skills, then an Appearance submenu. Document actions never include app settings. The reader's options menu starts with Undo saved changes when there is one, then groups Rename, Duplicate, Move to project, Details, and a Status submenu, then Delete; Previous exports is reached from the Export dropdown in the reader and from each card's options menu in the library, and its archive icon is distinct from the clock used only for version history. Compact layouts expose reading controls through the page counter. Comments and History share one side panel that docks beside the pages, pushing them over, and becomes a bottom sheet on narrow screens; the toolbar's Comments and History buttons open its tabs and stay marked while their tab is showing. The Comments button carries the open-comment count as a small badge, hidden at zero and included in its accessible name. Document cards lead with the real preview, then the title and compact metadata. Keep secondary text readable; avoid uppercase micro-labels, decorative badges, floating arrow ornaments, and motion on the paper. Feedback uses compact rows with page/component labels, comment text, and pencil/trash actions. A compact selection bar holds labelled Edit, Comment, and History actions; a separate save bar with pending changes, undo/redo, Discard, and Save all appears only while there is something to save. Draft PDFs stay separate from saved source. Keyboard hints such as `kbd` shortcuts are hidden on touch screens.

## App color palette

`src/app/colors.css` owns the grayscale browser palette: `#F8F8F8` background and `#2777C1` primary accent. Use its semantic tokens throughout app styles, including surfaces, selection, errors, and shadows. Small interactive labels use the darker `--accent-ink` shade for contrast. Headings and secondary controls stay neutral. Status and error messages keep their explicit wording; color is not their only signal. The app supports light, dark, and system appearance, with stronger foregrounds/borders for increased contrast. PDF themes, theme swatches, and supplied media retain their own colors.
